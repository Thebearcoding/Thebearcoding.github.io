Agent 的分数不像分类准确率那样一眼就能看懂。同样写着“成功率 30%”，背后可能是隐藏单元测试判分、数据库状态比对、字符串精确匹配，也可能是另一个 LLM 打的分，而且同一个模型换一套脚手架（scaffold）分数能差好几倍。面试官问“你怎么评测 Agent”，想听的是你能说清楚：**任务从哪来、环境给什么、判分器怎么判、指标怎么算、数字有多大误差**。这一篇按这个顺序过一遍六个常见基准，讲清 pass@k 和 pass^k 的区别，再讲怎样从轨迹里做失败分析，最后讲评测里的坑。训练侧的奖励设计见 [Agent RL 进阶](/notes/agent-rl-advanced/)，工具调用的消息格式见 [工具调用](/notes/agent-tool-calling/)，本篇不重复。

阅读入口：[Agent 专题总览](/notes/agent-guide/)。数值算例为教学构造；论文数字均注明表号或页面日期。

## 1. 评测的四个部件

把一次 Agent 评测写成一个函数：输入任务 $x$（自然语言指令，有时带文件或初始环境状态），Agent 与环境交互产生轨迹 $\tau=(a_1,o_1,a_2,o_2,\dots,a_T)$，判分器 $g(x,\tau,s_T)\in\{0,1\}$ 或 $[0,1]$ 给分，其中 $s_T$ 是环境的终态。一条轨迹在日志里通常是一个消息列表：

```
[{"role":"user","content":"..."},
 {"role":"assistant","tool_calls":[{"name":"search","arguments":{"q":"..."}}]},
 {"role":"tool","content":"..."}, ...,
 {"role":"assistant","content":"FINAL ANSWER: 17"}]
```

四个部件决定了这个基准测的是什么：

| 部件 | 要问的问题 | 例子 |
|---|---|---|
| 任务来源 | 人写、模板生成、还是从真实数据爬取？会不会进了预训练语料？ | SWE-bench 爬 GitHub；WebArena 用模板实例化 |
| 环境 | 静态（只看最终输出）还是可交互、有状态？能否复现？ | τ-bench 有数据库和模拟用户；BFCL 多为单轮 |
| 判分器 | 看结果还是看过程？规则、执行，还是 LLM 裁判？ | 单元测试、数据库比对、精确匹配、AST 匹配 |
| 指标 | 单次成功率、多次采样至少一次成功、还是多次全部成功？ | % Resolved、pass@k、pass^k |

**验证一个基准是否可信**的三件事：判分器的假阴性（正确解被判错）、假阳性（错误解被判对）、环境搭建失败率。SWE-bench Verified 就是专门处理前两件事的产物（第 2 节）。

## 2. SWE-bench 与 SWE-bench Verified

**任务。** SWE-bench（Jimenez et al., arXiv 2310.06770，ICLR 2024）给模型一个 Python 仓库的代码快照和一段 GitHub issue 文本，要求生成一个补丁（patch）解决问题。测试集有 2,294 个任务，来自 12 个流行 Python 仓库。构造分三步（论文 §2.1）：从约 9 万个 PR 中选仓库并爬取；按属性过滤，保留“关联了 issue、改了测试文件、已合并”的 PR；按执行过滤，要求至少有一个测试在应用参考补丁前失败、应用后通过。

**判分。** 每个任务有两组测试：`FAIL_TO_PASS`（补丁前失败、补丁后通过，验证问题已修）和 `PASS_TO_PASS`（前后都通过，验证没有改坏别的功能）。两组全过才算 resolved，指标是 **% Resolved**。测试对 Agent 不可见。参考补丁平均改 1.7 个文件、3.0 个函数、32.8 行（摘要与 Table 1），这说明任务需要跨文件定位。论文摘要报告最好的模型 Claude 2 只解决 1.96%（BM25 检索设定，对应 Table 5）。

**SWE-bench Lite**（官方页面）是 300 个测试实例，覆盖 12 个仓库中的 11 个。过滤条件包括：问题描述不含图片和外链、不少于 40 词、参考补丁只改一个文件且不超过 3 个 hunk、不新建或删除文件等。它通过挑简单题让评测更便宜。

**SWE-bench Verified**（OpenAI 官方说明，2024-08-13 发布，页面标注 2025-02-24 更新）。OpenAI 指出原测试集有三类问题：单元测试过于具体甚至与 issue 无关，导致正确解被判错；issue 描述欠明确；环境难以可靠搭建。做法是请 93 名有 Python 经验的开发者标注 1,699 个随机样本，每个样本由 3 人独立标注，按 0–3 级严重度打“问题描述是否欠明确”和“`FAIL_TO_PASS` 测试是否会误杀正确解”两项，取三人中最严重的标签，2 级及以上即剔除。结果 38.3% 被标为描述欠明确，61.1% 被标为测试可能误判，总计 68.3% 被过滤。最终抽出 **500 个样本**，其中 196 个估计耗时不到 15 分钟（easy），45 个超过 1 小时（hard）。同时发布了基于 Docker 容器的新评测框架。页面报告 GPT-4o（`gpt-4o-2024-05-13`）在最好的开源脚手架下 Verified 解决率 33.2%，原 SWE-bench 上为 16%。

**边界。** 同一页面强调：Lite 是通过挑简单题变容易，Verified 是通过剔除不可解的题变“公平”；按难度分层后，Verified 在同一难度桶内的解决率也上升，这才说明它去掉的是坏题而不只是难题。另外，页面明确承认任务来自公开 GitHub，预训练模型很可能已被污染（第 10 节）。

## 3. GAIA：问题简单、过程很长

**任务。** GAIA（Mialon et al., arXiv 2311.12983，ICLR 2024）共 466 个问题，答案是简短、无歧义的事实：一个数字、一个字符串或逗号分隔的列表。其中 300 题的答案不公开，用于排行榜；其余 166 题带答案公开。摘要列出的能力要求是推理、多模态处理、网页浏览和工具使用。

**难度分级**（论文原文定义）：

| 级别 | 定义（论文原意） | 题数（Table 4） |
|---|---|---:|
| Level 1 | 通常不需要工具，或至多一个工具，不超过 5 步 | 146 |
| Level 2 | 约 5–10 步，需要组合不同工具 | 245 |
| Level 3 | 面向近乎完美的通用助手：任意长的动作序列、任意多工具、需要接触外部世界 | 75 |

**判分。** 准精确匹配：对答案做一定归一化后与标准答案比较，不用 LLM 裁判。这正是 GAIA 的设计取向：过程开放，结果可自动核对。

**结论。** 人类答题者总体 92%，GPT-4 加插件 15%（摘要）；分级看，GPT-4 加插件在 Level 1/2/3 上分别为 30.3%、9.7%、0%（Table 4）。

**边界。** 网页内容随时间变化，过去能查到的答案可能失效，复现时要记录评测日期。答案格式稍有偏差（单位、千分位逗号）就会判错，所以要把输出格式约束写进系统提示，并单独统计“格式错误”这一类失败。

## 4. τ-bench：和用户对话，还要守规矩

**任务。** τ-bench（Yao et al., arXiv 2406.12045，2024-06）模拟客服场景：Agent 拿到领域 API 工具和一份政策文档（例如什么情况下可以退改），与一个由 LLM 扮演的用户多轮对话，完成用户诉求。两个领域：τ-retail 115 个任务，τ-airline 50 个任务。用户模拟器是 `gpt-4-0613`，论文 §5 写明温度为 Agent 0.0、用户 1.0。

**判分。** 对话结束后比较数据库终态与标注的唯一正确终态是否完全一致，同时检查 Agent 的回复是否包含了必要信息。这是看结果的客观判分，不依赖 LLM 裁判。

**结论。** Table 2 中函数调用方式的 gpt-4o 在 retail 上 pass^1 为 61.2%，airline 上为 35.2%；摘要说 retail 上 pass^8 低于 25%（Fig. 4）。主结果每个任务至少跑 3 次。论文 Fig. 5 分析了 36 条 gpt-4o 在 retail 上失败的轨迹，归为三类：提供了错误的参数或信息、决策错误（没守住领域规则）、对复合请求只解决了一部分。

**边界。** 用户模拟器本身会出错，例如提前说出全部信息或偏离任务指令，这会把模拟器的错误算到 Agent 头上。即使 Agent 温度为 0，用户温度为 1，同一任务每次对话仍不同，这正是 pass^k 要度量的东西（第 8 节）。

## 5. WebArena：自托管网站上的真实操作

**环境。** WebArena（Zhou et al., arXiv 2307.13854，ICLR 2024）自托管四类网站：电商（OneStopShop）、论坛（基于 Postmill）、协作开发（GitLab）、内容管理（Magento 后台），外加地图（OpenStreetMap）、计算器、草稿本和维基百科等辅助工具。论文强调环境可复现、可自托管。

**输入输出。** 观测可选可访问性树（accessibility tree）、HTML DOM 或截图，可限制在当前视口；动作分三类：元素操作（click、hover、type、按键组合）、标签页操作（新开、关闭、切换）、URL 导航（goto、前进、后退）。

**任务与判分。** 812 个任务，由 241 个模板实例化（平均每模板 3.3 个）。判分是**功能正确性**：信息查询类任务对答案用 `exact_match`、`must_include` 或 `fuzzy_match`；操作类任务用程序检查网站数据库或页面状态（例如订单是否真的生成）。部分任务设计为不可完成，期望 Agent 回答 “N/A”。

**结论**（Table 2）。GPT-4 加 CoT、提示中告知“任务可能不可完成”时成功率 11.70%，去掉这条提示后为 14.41%；人类为 78.24%。这个对比本身是一个教训：提示里一句话就能让 Agent 过度放弃，评测时提示词必须固定并公开。

## 6. BFCL：AST 评估与执行评估

BFCL（Berkeley Function Calling Leaderboard）只测“给定工具文档，模型能否写出正确的函数调用”，不测长程任务。以下依据官方博客（页面标注 2024-08-19 更新）。

**任务。** 初版 2,000 个“问题—函数—答案”三元组：Python 1,680、Java 100、JavaScript 50、REST API 70、SQL 100。按调用形态分为 Simple（一个函数、调一次）、Multiple（2–4 个候选函数中选一个）、Parallel（一句话触发多次调用）、Parallel Multiple（二者结合），另有 Relevance Detection：给的函数都不相关，期望模型**不调用**。

**AST 评估。** 把模型输出解析成抽象语法树，依次检查：函数名是否匹配；必填参数是否都在；每个参数的类型与取值是否落在标注的“可接受取值列表”里（类型检查很严格，可选参数单独处理）。好处是不用真的执行，Java、JavaScript 这类无法直接运行的调用也能判。

**执行评估。** 真的执行生成的调用，比较返回结果：非 REST 函数用精确匹配、实时数据的 ±20% 容差匹配或结构匹配；REST API 检查能否成功执行、返回类型是否正确、JSON 键是否一致。

**为什么两者都要。** AST 判的是“写得像不像标注”，可能误杀等价写法（例如另一种合法的日期格式不在可接受列表里）；执行判的是“跑出来对不对”，但依赖外部服务稳定，且执行有副作用的函数有风险。面试里可以说：AST 是低成本、可复现的近似，执行评估是更接近真实但更脆弱的金标准。

**版本。** 排行榜已到 V4（页面标注 2026-04-12 更新），后续版本加入了多轮和 agentic 类别，总分是各子类的不加权平均，并同时报告成本与延迟。各版本子类构成随版本变化，引用分数时要写版本号。

## 7. AgentBench：八个环境的综合测验

AgentBench（Liu et al., arXiv 2308.03688，ICLR 2024）把 8 个环境放在同一框架下测 LLM 作为 Agent 的能力：代码类（操作系统、数据库、知识图谱）、游戏类（数字卡牌游戏、横向思维谜题、家务 House-Holding）、网页类（网购 Web Shopping、网页浏览 Web Browsing）。各环境指标不同：OS、DB、家务为成功率，知识图谱为 F1，卡牌为胜率，谜题为游戏进度，网购为奖励分，网页浏览为步骤成功率。开发集与测试集合计 269 和 1,014 个样本，论文测了 29 个 API 和开源模型。

两点值得记住。① **总分归一化**：各任务指标量纲不同，论文先把每个任务的平均分缩放到 1 再求平均，并把“所有被测模型在该任务上平均分的倒数”固定为权重。② **失败结果分类**：Table 4 统计了五种执行结果的占比：Context Limit Exceeded、Invalid Format、Invalid Action、Task Limit Exceeded 和 Complete。这是一种最粗粒度、可以自动统计的失败分类，第 9 节在此基础上细化。论文结论是开源模型与顶级商用模型差距明显，主要障碍是长程推理、决策和指令遵循。

## 8. pass@k 与 pass^k

**pass@k**（Codex，Chen et al., arXiv 2107.03374，§2.1）：每题采 $k$ 个样本，**至少一个**通过就算解决。直接只采 $k$ 个估计方差大，于是每题采 $n\ge k$ 个（论文用 $n=200$，$k\le100$），数出通过数 $c$，用无偏估计（式 (1)）：

$$
\text{pass@}k=\mathbb E_{\text{problems}}\left[1-\frac{\binom{n-c}{k}}{\binom{n}{k}}\right].
$$

$\binom{n-c}{k}/\binom{n}{k}$ 是“从 $n$ 个样本里无放回抽 $k$ 个、全部抽到失败样本”的概率。论文指出用 $1-(1-\hat p)^k$（$\hat p=c/n$）估计是有偏的（附录 A），并给了逐项连乘的数值稳定实现（Fig. 3）：`1 - np.prod(1 - k / np.arange(n - c + 1, n + 1))`，当 $n-c<k$ 时直接返回 1。

**pass^k**（τ-bench）：同一任务独立跑 $k$ 次，**全部**成功才算。无偏估计形式对称：

$$
\text{pass}^k=\mathbb E_{\text{task}}\left[\frac{\binom{c}{k}}{\binom{n}{k}}\right].
$$

若单次成功率为 $p$ 且各次独立，则 $\text{pass@}k=1-(1-p)^k$ 随 $k$ 增大而上升，$\text{pass}^k=p^k$ 随 $k$ 增大而下降。前者衡量“能力上限”（多试几次总能做对，适合有验证器可以挑答案的场景，如代码有单测），后者衡量“可靠性”（面对真实用户只有一次机会，客服 Agent 每次都得对）。$k=1$ 时两者相等，都是平均单次成功率。

**手算 1：$n=10$，$c=3$**（教学构造）。

- pass@1 $=1-\binom{7}{1}/\binom{10}{1}=1-7/10=0.3$，就是 $c/n$。
- pass@3 $=1-\binom{7}{3}/\binom{10}{3}=1-35/120=85/120\approx0.708$。
- 对照有偏的代入法：$1-(1-0.3)^3=1-0.343=0.657$，比无偏估计低约 5 个百分点。
- 同一组数据的 pass^3 $=\binom{3}{3}/\binom{10}{3}=1/120\approx0.008$：能做出来，但几乎不可能连续三次都做对。

**手算 2：单次成功率 0.8 时的 pass^4**（教学构造）。$\text{pass}^4=0.8^4=0.4096$，而 $\text{pass@}4=1-0.2^4=0.9984$。一个“80% 成功率”的 Agent，连续服务同一类请求 4 次全对的概率只有约 41%。若实际只跑了 $n=10$ 次、成功 $c=8$ 次，无偏估计给出 $\binom84/\binom{10}4=70/210\approx0.333$，代入法给出 $0.8^4=0.4096$；两者差异来自小样本，估计量在对任务的期望意义下无偏，单个任务上的读数仍有很大波动，所以 $n$ 要明显大于 $k$。

**边界。** ① pass@k 假设能免费挑出正确样本；没有验证器时报 pass@k 会夸大实用性能，应报 pass@1 或“带选择器的 best-of-k”。② 各次运行不独立时（例如共用缓存、同一个被污染的网页），$p^k$ 不再成立，只能用经验估计。③ $n<k$ 时两个估计量都无定义。

## 9. 轨迹级失败分析

成功率只告诉你“错了多少”，改进需要知道“错在哪一步、为什么错”。做法分四步：

1. **定位首个错误步。** 对每条失败轨迹，找出第一个让任务不可能再成功的动作（例如参数写错的那次工具调用），而不是最后报错的那一步。后续错误多是连锁反应。
2. **按固定分类打标签。** 分类要互斥、可操作，每类对应一个改进方向。可从 AgentBench 的五类执行结果和 τ-bench 的三类失败出发细化。
3. **区分 Agent 的错与评测的错。** 环境故障、判分器误判不该计入模型能力，但要单独报告。
4. **抽样复核。** 用 LLM 辅助打标签时，人工复核一部分并报告一致率。

**手算：一份失败分类统计**（教学构造，数字全部虚构）。200 个任务跑一次，成功 150，失败 50：

| 类别（首个错误步） | 条数 | 占失败 | 对应改进 |
|---|---:|---:|---|
| 工具参数错误（类型、取值、ID 写错） | 14 | 28% | 工具 schema 更严、参数校验报错回传 |
| 违反领域规则/政策 | 9 | 18% | 政策检索、动作前自检 |
| 过早结束（未完成就作答） | 7 | 14% | 完成条件清单、验证步骤 |
| 选错工具 | 6 | 12% | 工具描述、工具检索 |
| 循环或步数超限 | 5 | 10% | 重复检测、规划 |
| 输出格式/解析失败 | 4 | 8% | 约束解码、格式提示 |
| 环境故障（超时、容器起不来） | 3 | 6% | 重试、基础设施 |
| 判分器误判（人工复核为正确） | 2 | 4% | 修判分器 |
| 合计 | 50 | 100% | |

读法：模型侧失败 45 条，前三类占 30 条，即三分之二，优先做参数校验和政策遵循。环境与判分问题 5 条：报告的成功率是 $150/200=75\%$；若把 2 条误判改判为成功，成功率是 $152/200=76\%$；3 条环境故障应重跑而不是直接计为失败。改了之后要做消融：只加参数校验，看“工具参数错误”这一类是否下降、其他类是否上升（例如校验报错导致循环增多）。

## 10. 评测的坑

**数据污染。** SWE-bench 来自公开 GitHub，OpenAI 的 Verified 说明页直接承认预训练模型很可能已见过这些任务。检查手段：按 issue 创建时间切分，比较模型训练截止日期前后的成功率；用 n-gram 重叠或让模型续写 issue/补丁来探测记忆；优先用答案不公开的测试集（GAIA 保留 300 题答案）或持续更新的新题。

**非确定性与置信区间。** 采样温度、用户模拟器、网页内容、API 返回、并发时序都会让同一 Agent 两次跑分不同。最低要求是报告运行次数和标准误。**手算**（教学构造）：500 题、成功率约 50%，单次运行的标准误 $\sqrt{0.5\times0.5/500}\approx0.0224$，95% 置信区间约 $\pm4.4$ 个百分点；165 题时约 $\pm7.6$ 个百分点。因此在 500 题的基准上，两个系统差 2 个百分点，单跑一次不足以下结论。可改用同一任务集上的配对比较（逐题看谁对谁错），或多跑几次取平均。

**成本与延迟。** Agent 每一步都把历史重新喂给模型，输入 token 随步数累积。**手算**（教学构造，单价为假设）：500 个任务，平均 40 步，每步平均输入 30k token、输出 500 token；输入共 $500\times40\times30\text{k}=6\times10^8$，输出 $500\times40\times500=10^7$。若单价为输入 1 美元/百万 token、输出 5 美元/百万 token，一次全量评测约 $600+50=650$ 美元，算 pass^4 要再乘 4。降本手段有前缀缓存、上下文压缩、先在小子集上筛选配置。排行榜只看成功率会奖励“堆步数”的系统，应同时报告每任务成本和端到端延迟（BFCL V4 排行榜就同时报这两项）。

**LLM 裁判偏差。** 开放式任务常让 LLM 当裁判。MT-Bench 论文（Zheng et al., arXiv 2306.05685，NeurIPS 2023 D&B）点名了位置偏差（偏向先出现或后出现的回答）、冗长偏差（偏向更长的回答）、自我偏好（偏向自己生成的回答），以及推理能力有限；同时报告 GPT-4 裁判与人类偏好的一致率超过 80%，与人类之间的一致率相当。对策：成对比较时交换顺序各判一次；给出明确评分细则与参考答案；裁判模型与被测模型不同源；抽样人工标注，报告裁判与人的一致率。能用规则或执行判分（单测、数据库比对、精确匹配）时，就不要用 LLM 裁判，这也是本篇六个基准的共同选择。

**脚手架差异。** OpenAI 的说明页举例：GPT-4 在 SWE-bench Lite 上用早期 RAG 脚手架为 2.7%，用 CodeR 为 28.3%。比较“模型”时必须固定脚手架、工具集、步数上限和提示词；比较“系统”时则要把这些写进结果表。

## 11. 面试常问

**pass@k 和 pass^k 分别适用于什么场景？** pass@k 衡量多次尝试中至少一次成功，前提是有可靠验证器能挑出对的那次（代码单测、数学验算），适合衡量潜力或 RL 训练前的可学性。pass^k 衡量 k 次全部成功，适合面对真实用户、没有重试机会的场景。单次成功率 0.8 时，pass^4 只有约 0.41。

**为什么不能直接用 $1-(1-c/n)^k$ 算 pass@k？** 它是有偏估计。无偏估计是 $1-\binom{n-c}{k}/\binom{n}{k}$，即无放回抽 $k$ 个全失败的概率取补。$n=10$、$c=3$、$k=3$ 时，无偏值约 0.708，代入法得 0.657。

**SWE-bench Verified 和原版有什么不同？** 由专业开发者三人标注，剔除描述欠明确和单元测试会误杀正确解的样本，留下 500 题，并配套 Docker 评测框架。目的是减少假阴性，不是单纯变简单；分难度看，同一难度桶内解决率也上升。

**AST 评估和执行评估各有什么问题？** AST 便宜、可复现，但只能和标注的可接受取值比对，会误杀等价写法；执行评估更接近真实，但依赖外部服务、可能有副作用、结果随时间变化。

**你的 Agent 成功率从 60% 涨到 62%，能说明变好了吗？** 先看题数和运行次数：500 题单次运行的 95% 置信区间约 ±4.4 个百分点，不够。做逐题配对比较、多跑几次，并看失败分类的变化，确认提升来自目标类别而不是环境波动。

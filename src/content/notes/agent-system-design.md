系统设计题考的不是背一个架构图，而是**在有限时间里把模糊需求变成可衡量的目标，再把每个设计选择和它的代价对应起来**。这一篇先给一个固定的答题框架，然后用两个例子走一遍：deep research（多智能体、长任务、成本敏感）和多模态客服（有图片输入、有真实的错误代价、需要人工兜底）。算法细节都在各专题教程里，这里只讲怎样把它们组装起来，以及怎样当场算账。

阅读入口：[Agent 总览](/notes/agent-guide/)。数值算例为教学构造，单价为假设值，实际以所用模型的定价为准。

## 1. 答题框架：八步

| 步 | 要做什么 | 产出 | 常见失分 |
|---|---|---|---|
| 1. 澄清需求 | 用户是谁、输入输出是什么、规模多大、能容忍多慢、错了有多严重 | 三五条约束 | 直接画架构 |
| 2. 定指标 | 任务成功率、pass^k、延迟（首字、端到端）、单任务成本、安全违规率 | 一张指标表 | 只说“效果好” |
| 3. 先给最简方案 | 单次调用或固定 workflow 能否解决 | 基线 | 一上来就多智能体 |
| 4. 架构 | workflow 还是 agent；单 Agent 还是主从；哪些步骤并行 | 框图加数据流 | 不说为什么拆 |
| 5. 上下文与工具 | 每一步模型看到什么；工具集、schema、权限；压缩与外部化 | 上下文预算 | 工具一股脑全给 |
| 6. 评测 | 离线评测集怎样建、怎样判定；线上指标；配对比较 | 评测方案 | 没有判定标准 |
| 7. 成本与延迟 | token 账、延迟账、并发与限流 | 三个数字 | 不会估算 |
| 8. 安全与运维 | 提示注入、越权、费用失控；日志、回滚、人工兜底 | 风险清单 | 只字不提 |

第 3 步最容易被跳过，却最能体现判断力。Anthropic 的 *Building effective agents* 明确建议先找最简单的方案，只在必要时增加复杂度，因为 agent 系统通常用延迟和成本换效果。面试时先说“如果需求只是 X，一个固定的检索加总结流程就够了；但因为有 Y 和 Z，才需要 agent”，比直接画多智能体图更有说服力。

## 2. 主例：deep research

**题目**：设计一个调研助手，用户给一个开放问题（“对比三家云厂商的 GPU 实例价格与可用性”），系统搜索网页、阅读、整理，输出一份带引用的报告。

**澄清需求（第 1 步）**：报告长度两三千字；可以接受几分钟的等待；每份报告的成本要可控；引用必须能点开核实；峰值每秒约 1 个新任务。

**指标（第 2 步）**：

| 指标 | 怎样测 |
|---|---|
| 事实正确率 | 抽取报告里的事实陈述，对照引用逐条核实（忠实度做法见 [Agent RAG](/notes/agent-rag/) 第 7 节） |
| 覆盖度 | 人工为每道题列出“应该提到的要点”，统计覆盖比例 |
| 引用准确率 | 引用的网页是否真的支持对应句子 |
| 端到端延迟、单任务成本 | 日志统计，按 P50、P95 报告 |

**最简方案（第 3 步）**：一次搜索、取前 10 个结果、一次总结。它对“一个方面就能回答”的问题够用，但对比类、多跳类问题会漏掉大量信息，这正是需要 agent 的理由。

**架构（第 4 步）**：主从结构（orchestrator-worker）。主 Agent 拆分调研方向，派出 4 个子 Agent 并行搜索与阅读，各自返回结构化摘要（结论、证据链接、不确定点），主 Agent 综合成报告。拆分的理由是 [MCP 与多智能体](/notes/agent-mcp-multiagent/) 第 6 节的三条：子方向可以并行；每个子 Agent 读大量网页，需要上下文隔离；主 Agent 只拿压缩后的结论。Anthropic 的多智能体调研系统用的就是这个结构，报告在内部评测上比单 Agent 高 90.2%，token 用量约为普通对话的 15 倍。

**上下文与工具（第 5 步）**：子 Agent 只有 `search` 和 `fetch` 两个工具；网页正文先截断或抽取相关段落再放进上下文；子 Agent 的提示里写清边界（“只调研厂商 A”“只要 2026 年的数据”），避免重复工作。

### 2.1 第一笔账：token 与成本

设定（教学构造）：

- 主 Agent 规划：输入 5000，输出 800；
- 每个子 Agent 基础提示 3000，共 8 轮，每轮输出 300 token（思考加调用），工具返回 2000 token；最后写 1000 token 的摘要；
- 主 Agent 综合：输入 = 规划时的 5000 + 800 + 4 份摘要各 1000 = 9800，输出 3000；
- 假设单价：输入 3 美元 / 百万 token，输出 15 美元 / 百万 token，缓存命中的输入 0.3 美元 / 百万 token（忽略写缓存的额外费用）。

**子 Agent 的输入**：第 $r$ 轮的输入是基础提示加前面所有轮的输出与工具结果，$3000+2300(r-1)$。8 轮合计

$$
\sum_{r=1}^{8}\big(3000+2300(r-1)\big)=24\,000+2300\times28=88\,400.
$$

输出 $8\times300+1000=3400$。

**整个任务**：输入 $5000+4\times88\,400+9800=368\,400$，输出 $800+4\times3400+3000=17\,400$。

| | 输入费用 | 输出费用 | 合计 |
|---|---:|---:|---:|
| 不用前缀缓存 | $0.3684\text{M}\times3=1.105$ | $0.0174\text{M}\times15=0.261$ | **1.37 美元** |
| 用前缀缓存 | 未命中 86 200 token × 3 + 命中 282 200 token × 0.3 = 0.343 | 0.261 | **0.60 美元** |

用缓存时每个子 Agent 只有第 1 轮的 3000 和之后每轮新增的 2300 是未命中：$3000+2300\times7=19\,100$；其余 69 300 都命中。综合那一步与规划共享 5000 的前缀。**输入占了成本的大头，前缀缓存把总成本降到约 44%**；剩下的主要是输出费用和每轮新增的工具结果。进一步省钱的方向：截断工具返回（每轮 2000 降到 1000，子 Agent 输入几乎减半）；子 Agent 换成更便宜的模型；减少轮数上限。

### 2.2 第二笔账：延迟

设每次模型调用 5 秒、每次工具调用 3 秒（教学构造）。主 Agent 规划 8 秒；子 Agent 每轮 8 秒，8 轮 64 秒，加写摘要 6 秒，共 70 秒，4 个并行；综合 20 秒。端到端 $8+70+20=98$ 秒。

关键路径是最慢的那个子 Agent，所以 P95 延迟取决于子 Agent 轮数和工具延迟的尾部。缩短的手段：给子 Agent 设轮数和时间上限；工具调用超时就跳过；综合阶段流式输出，让用户更早看到内容。

### 2.3 第三笔账：并发（Little 定律）

Little 定律：稳态下系统中的平均任务数 $L=\lambda W$，$\lambda$ 是到达率，$W$ 是每个任务在系统里的停留时间。

峰值 $\lambda=1$ 个任务 / 秒，$W=98$ 秒，同时在跑的任务约 $L=98$ 个。子 Agent 只在中间 70 秒活跃，同时在跑的子 Agent 数约 $1\times4\times70=280$。搜索调用：每个任务 $4\times8=32$ 次，平均 32 次 / 秒。

这三个数直接决定了容量规划：模型服务要能承受约 300 路并发会话，搜索 API 的配额至少 32 QPS（还要留出重试余量），否则任务会排队，$W$ 变长，$L$ 进一步上升。超出容量时的策略要提前设计：排队并告知预计时间、降级为单 Agent 简版报告，或者限流。

### 2.4 评测与安全

**评测（第 6 步）**：准备 50–100 道代表性问题，每题人工列出必须覆盖的要点；每次改动在同一组题上做配对比较（方法见 [Agent 评测](/notes/agent-eval/) 第 6 节）；LLM 裁判先在人工标注集上测 kappa。过程指标也要看：子 Agent 之间的重复搜索率、触顶比例、引用失效率。

**安全（第 8 步）**：网页内容可能含提示注入，子 Agent 只给只读工具；报告里的每个事实必须带引用；记录完整的调用树，出问题时能追到是哪个子 Agent、哪个网页；单任务设费用上限。

## 3. 副例：多模态客服

**题目**：电商客服 Agent，用户可以上传照片（“收到的杯子碎了”），系统核实订单、判断是否符合退换政策、给出处理方案。

**和主例的差别**：一是输入有图片；二是**错误有直接的金钱代价**（错误退款），也有体验代价（错误拒绝）；三是对延迟敏感，用户在等回复；四是有明确的政策文档和订单系统可以作为依据。

**澄清需求**：首条回复 3 秒内；退款金额超过阈值必须人工审批；要能处理文字、图片、订单号混合的输入；每天约 1 万个工单，其中约 30% 涉及退款。

**架构**：这里适合**以 workflow 为主、局部 agent**，因为主流程是可预知的：

1. 意图分类（小模型）：咨询、退换、投诉、其他；
2. 订单查询（工具，按用户身份做权限校验）；
3. 图片核验（VLM）：图中是否是该订单的商品、损坏是否可见、是否与描述一致；
4. 政策检索（RAG）：取回相关条款；
5. 决策：在规则允许的范围内由模型给方案，超出阈值或置信度低时转人工；
6. 回复生成，附上依据（订单状态、政策条款）。

只有第 5 步需要模型做开放判断，其他步骤都可以用固定流程加校验。这正是第 1 节第 3 步“先给最简方案”的体现。

**图片的成本**：以 Qwen2.5-VL 为例，每个视觉 token 对应 $28\times28$ 像素，一张缩放到 $1288\times728$ 的照片是 $46\times26=1196$ 个视觉 token（计算见 [视觉定位](/notes/multimodal-grounding/) 第 3 节）。这比一轮文字对话多一个数量级，而且 prefill 直接影响首条回复的延迟。手段：先用小模型判断是否需要看图；对需要细看的区域裁剪放大，而不是整图高分辨率；同一张图在多轮对话里复用缓存。

**错误代价手算**（教学构造）：每天 3000 个退款请求，平均金额 150 元。如果全部自动审批、错误批准率 2%，每天错误退款 $3000\times0.02\times150=9000$ 元。设一个金额阈值：低于阈值自动处理，高于阈值转人工。阈值的选择是一个明确的权衡：人工审核的成本（每单多少钱、多少分钟）对比错误退款的期望损失，以及自动处理带来的等待时间缩短。面试时把这个权衡说出来，比说“用一个更强的模型”有用得多。

**幻觉风险**：VLM 可能“看到”图里没有的损坏，或者对模糊图片过度自信。对策：要求模型输出判断依据（指出图中哪个区域）；对模糊图片要求用户补拍；用 POPE 式的是非题做离线评测，见 [多模态幻觉](/notes/multimodal-hallucination-eval/) 第 4 节。

**评测**：按 τ-bench 的思路，用模拟用户加模拟订单数据库构造场景测试，对话结束后检查数据库状态（是否退款、金额是否正确）；客服场景每次都必须做对，所以报告 pass^k 而不只是平均成功率（见 [Agent 评测](/notes/agent-eval/) 第 2 节）。线上看问题解决率、转人工率、错误退款率、用户满意度。

## 4. 面试常问

**为什么用多智能体，不用单 Agent？** 说清三个理由中哪几个成立（并行、上下文隔离、工具差异），给出成本对比（token 用量会成倍增加），并说明单 Agent 版本作为基线和降级方案。

**怎样估算成本？** 列出每次调用的输入输出 token，注意多轮时输入是累积的；分别算有无前缀缓存；指出成本的大头在哪里，以及对应的省钱手段。

**怎样估算需要多少并发？** Little 定律 $L=\lambda W$：峰值到达率乘以任务停留时间。再乘以每个任务的子 Agent 数和工具调用数，得到模型服务和下游 API 的容量需求。

**错误代价高的场景怎样设计？** 以 workflow 为主，开放判断只放在必要的一步；设阈值转人工；输出判断依据；用 pass^k 评测一致性；记录完整日志可以审计。

**怎样知道改动有没有用？** 固定评测集，同一脚手架下做配对比较，报告置信区间；同时看过程指标，防止只是“变得少说”或“变得保守”。

一个 Agent 改了提示词之后，在 100 个任务上的成功率从 62% 变成 68%。这算进步吗？要回答这个问题，需要知道这 100 个任务测的是什么、每个任务怎么判对错、同一个任务跑两次结果是否一样，以及 6 个点的差距在统计上是否可信。这一篇按这个顺序展开。RAG 系统的检索与忠实度评估见 [Agent RAG](/notes/agent-rag/) 第 7 节，多模态幻觉的评测见 [多模态幻觉与评测](/notes/multimodal-hallucination-eval/)。

阅读入口：Agent 专题（总览即将上线，可先从 [工具调用](/notes/agent-tool-calling/) 读起）。数值算例为教学构造；基准的细节以各自论文和官网为准。

## 1. 为什么 Agent 比单轮问答难评

**结果有随机性。** 温度大于 0 时，同一个任务跑多次结果不同。即使温度为 0，工具返回（搜索结果、网页内容）也可能变化。只跑一次得到的成功率本身就有噪声。

**过程有很多步。** 最终失败可能是第 2 步调错了工具，也可能是第 20 步写错了一个参数。只看最终结果，不知道该修哪里；只看过程，又可能惩罚了“走了不同路线但同样正确”的轨迹。

**环境会变。** 网页会更新、API 会改版、数据库状态会被前一个任务改动。一个今天能复现的结果，三个月后可能就复现不了。可复现的评测通常需要沙箱化的环境（Docker 容器、模拟的网站和数据库）。

**判对错本身就难。** 写代码可以跑单测，答事实题可以比对标准答案，但“写一份调研报告”“帮用户处理退款”的对错没有唯一标准。

## 2. 指标：不只是成功率

| 指标 | 定义 | 为什么要看 |
|---|---|---|
| 任务成功率 | 最终状态或答案符合要求的任务比例 | 主指标 |
| pass@k | $k$ 次尝试中至少一次成功的概率 | 能力上限，适合有验证器可以挑选的场景 |
| pass^k | $k$ 次尝试**全部**成功的概率 | 可靠性，适合每次都必须做对的场景 |
| 平均步数 / 调用次数 | 完成任务用的轮数和工具调用数 | 效率，也反映是否在打转 |
| 费用与延迟 | token 费用、墙钟时间 | 能否上线 |
| 安全违规率 | 执行了不该执行的操作的比例 | 高风险场景的硬约束 |

**pass@k 与 pass^k。** 设单次成功率 $p=0.7$，各次独立。pass@4 $=1-(1-0.7)^4=0.9919$；pass^4 $=0.7^4=0.2401$。同一个 Agent，前者说它“几乎总能做到”，后者说它“四次里全对的机会不到四分之一”。客服 Agent 每次面对用户都必须做对，看的是 pass^k；代码生成如果有单测可以从多个候选里挑，看的是 pass@k。τ-bench（Yao et al., arXiv 2406.12045）专门提出用 pass^k 衡量 Agent 的一致性，论文摘要报告，即使 gpt-4o 这样的函数调用 Agent，任务成功率也不到 50%，零售场景下 pass^8 不到 25%。

**无偏估计。** 实际中对每个任务采 $n$ 次，其中 $c$ 次成功，用组合数估计（Codex 论文，arXiv 2107.03374）：

$$
\widehat{\text{pass@}k}=1-\frac{\binom{n-c}{k}}{\binom{n}{k}},\qquad
\widehat{\text{pass}^k}=\frac{\binom{c}{k}}{\binom{n}{k}}.
$$

手算：$n=10$。若 $c=3$，$k=4$：$\binom{7}{4}/\binom{10}{4}=35/210$，pass@4 估计为 $1-0.1667=0.8333$。若 $c=7$，$k=4$：pass^4 估计为 $\binom74/\binom{10}4=35/210=0.1667$。直接把 $\hat p=c/n$ 代入 $1-(1-\hat p)^k$ 是有偏的：它对 $\hat p$ 做了非线性变换，期望不等于真值（$n$ 小时偏差明显）；组合数公式相当于从 $n$ 次结果里无放回地抽 $k$ 次，期望恰好等于真值。对所有任务的估计值取平均就是整体指标。

## 3. 主流基准各测什么

| 基准 | 任务 | 怎样判定 |
|---|---|---|
| SWE-bench / Verified | 修复真实 GitHub 仓库的 issue；完整版 2294 题 | 运行仓库的单测：原来失败的测试（fail-to-pass）要变成通过，原来通过的仍要通过；Verified 是 OpenAI 与原作者合作、请 93 位 Python 开发者人工审核后保留的 500 题子集（2024-08） |
| τ-bench | 模拟客服（零售、航空），Agent 与模拟用户多轮对话并调用工具 | 对话结束后数据库状态是否与标准一致，报告 pass^k |
| WebArena | 在自托管的网站（电商、论坛、协作开发、内容管理，另有地图等工具）上完成 812 个长程任务 | 检查页面状态或答案；论文里最好的 GPT-4 Agent 端到端成功率 14.41%，人类 78.24% |
| OSWorld | 在真实操作系统里用图形界面完成 369 个任务，涉及网页与桌面应用、文件读写、跨应用流程 | 每个任务配一个执行检查脚本 |
| GAIA | 需要搜索、多步推理、读文件的问答，共 466 题 | 每题只有一个正确答案（字符串、数字或列表），按答案类型归一化后做准精确匹配 |
| BFCL | 函数调用 | AST 匹配或执行匹配，见 [工具调用](/notes/agent-tool-calling/) 第 7 节 |

**读这些数字要注意的。** ① **版本**：SWE-bench 有完整版、Lite、Verified，不同版本的分数不能比。② **脚手架**：同一个模型配不同的 Agent 框架（工具集、提示、重试策略），分数差距可能比换模型还大。报告时要说明是“模型 + 哪个脚手架”。③ **污染**：基准题目来自公开仓库或网页，可能出现在训练数据里。④ **天花板**：一些基准的标注本身有错，分数接近天花板后的差距可能是噪声。

## 4. 怎样判对错：三类判定器

**基于规则 / 执行**：单测、状态比对、精确匹配。客观、可复现、便宜。缺点是只适用于结果可以被程序检查的任务，而且容易被钻空子（模型修改测试文件让测试通过）。所以判定器必须检查“怎样通过的”，比如 SWE-bench 用的测试在评测时才放进去，Agent 看不到。

**人工评估**：最可信，但贵、慢、不同标注者之间不一致。适合做小规模的校准集。

**LLM 当裁判**：用一个强模型按评分标准给输出打分或比较两个输出。便宜、可扩展，能处理开放式任务。MT-Bench 论文（Zheng et al., arXiv 2306.05685）报告，处理好偏差后 GPT-4 裁判与人类评审的一致率超过 80%，与人类评审之间的一致率相当；但它也列出了以下系统性偏差和局限：

- **位置偏差**：成对比较时偏向放在前面（或后面）的那个。对策：交换顺序各评一次，只有两次一致才算数。
- **长度偏差**：偏向更长、更详细的回答，即使内容并不更好。对策：评分标准里明确写“不因长度加分”，或者在长度相近的样本上分析。
- **自我偏好**：偏向与自己风格相近的输出，尤其是自己生成的。对策：裁判模型与被评模型来自不同家族。
- **能力上限**：裁判自己不会的题，它也判不准。

## 5. 校准裁判：和人工比一致性

上线一个 LLM 裁判之前，要在一个人工标注的小集上测它和人的一致性。不能只看准确率（一致的比例），因为两个“随便打分”的评委也会有一定比例碰巧一致。**Cohen's kappa** 扣掉了碰巧一致的部分：

$$
\kappa=\frac{p_o-p_e}{1-p_e},
$$

其中 $p_o$ 是实际一致的比例，$p_e$ 是按各自打分比例随机打分时的期望一致比例。

**手算**（教学构造）：100 个样本，裁判和人工各判“通过 / 不通过”。

| | 人工通过 | 人工不通过 |
|---|---:|---:|
| 裁判通过 | 50 | 15 |
| 裁判不通过 | 5 | 30 |

$p_o=(50+30)/100=0.80$。裁判判通过的比例 0.65，人工 0.55，$p_e=0.65\times0.55+0.35\times0.45=0.515$。$\kappa=(0.80-0.515)/(1-0.515)=0.588$。

80% 的一致率听起来不错，kappa 只有 0.59（按常用的 Landis–Koch 划分，0.41–0.60 是“中等”，0.61–0.80 是“较好”）。而且错误不对称：裁判把 15 个人工判不通过的放过了，只冤枉了 5 个，说明它**偏宽松**。用这个裁判评出的成功率会系统性偏高。改进方向是把评分标准写得更具体（列出必须满足的条款逐条判断），而不是笼统地问“这个回答好不好”。

## 6. 6 个点的差距是真的吗

**置信区间。** 100 个任务、成功率 62%，按二项分布的正态近似，标准误 $\sqrt{0.62\times0.38/100}=0.0485$，95% 置信区间约为 $62\%\pm9.5\%$。也就是说，同一个系统换 100 个同分布的任务再测，成功率落在 52.5%–71.5% 之间都不奇怪。68% 落在这个区间里。

**配对检验。** 两个版本在**同一组**任务上测时，应该用配对检验，它比把两个区间放在一起比更灵敏。只有两个版本结果不同的任务才提供信息。设 A 版本对、B 错的任务有 8 个，B 对、A 错的有 14 个（两者都对的 54 个，于是 A 是 62%、B 是 68%）。McNemar 检验（带连续性校正）：

$$
\chi^2=\frac{(|8-14|-1)^2}{8+14}=\frac{25}{22}=1.14,
$$

自由度为 1，$p\approx0.29$。**不显著。** 22 个有分歧的任务里 14 比 8，这种程度的偏向在两个版本实际一样好的情况下也经常出现。

**怎么办。** ① 增加任务数：标准误按 $1/\sqrt n$ 下降，要把区间缩小一半需要 4 倍的任务。② 每个任务跑多次取平均，降低单次运行的随机性。③ 报告时同时给出置信区间和任务数，不要只报一个点估计。④ 提前定好要比较的指标，避免在很多指标里挑一个显著的报告。

## 7. 轨迹评估：看过程

最终结果告诉你“错了”，轨迹告诉你“错在哪”。常用的过程检查：

- **工具选择**：每一步调用的工具是否合理（可以对照标准轨迹，但要允许等价的替代路线）；
- **参数正确性**：参数是否符合 schema 和语义；
- **冗余**：是否有重复调用、无效步骤；
- **恢复能力**：遇到工具错误后是否正确处理；
- **安全**：是否执行了未授权的操作。

做法是先跑一批任务，按失败原因人工分类（“没找到文件”“参数格式错”“过早结束”“幻觉了工具结果”），统计各类的比例。这比任何自动指标都更能指导下一步改什么。分类做过一两轮之后，可以把常见类别写成自动检查。

## 8. 搭一个自己的评测集

公开基准有用，但不能代替你自己业务上的评测。

1. **收集任务**：从真实使用日志、用户反馈和已知失败案例里取 50–200 个，覆盖常见场景和困难边界；
2. **定义成功**：每个任务写清楚怎样算成功，最好能程序化检查（最终状态、关键字段），开放式任务写具体的评分条款；
3. **固定环境**：工具返回用录制好的结果或沙箱，保证可复现；
4. **分层报告**：按任务类型、难度分别报告，避免总分掩盖某类任务的退步；
5. **持续更新**：每发现一个新的线上失败，就加进评测集（回归测试）；
6. **防止过拟合**：留一部分任务不用于日常调试，只在大版本时测。

## 9. 面试常问

**pass@k 和 pass^k 有什么区别？各用在哪？** pass@k 是 $k$ 次里至少一次成功，衡量能力上限，适合有验证器可以挑选的场景；pass^k 是 $k$ 次全部成功，衡量一致性，适合每次都必须做对的场景（客服）。$p=0.7$ 时 pass@4 约 0.99，pass^4 约 0.24。

**LLM 当裁判有哪些问题？怎么缓解？** 位置偏差（交换顺序评两次）、长度偏差（标准里明确不因长度加分）、自我偏好（用不同家族的模型）、能力上限。上线前在人工标注集上测 kappa，并检查错误是否偏向一边。

**怎样判断一次改进是否显著？** 在同一组任务上用配对检验（McNemar），只有两个版本结果不同的任务提供信息；同时报告置信区间。100 个任务的成功率，95% 区间约 ±10 个点。

**SWE-bench 分数高说明什么，不说明什么？** 说明在“真实仓库 + 有单测”的修 bug 任务上能力强。不说明在没有单测的开放任务、更大的代码库或者需要和人反复沟通的场景下同样好；而且分数和脚手架强相关。

**你怎样评测自己做的 Agent？** 公开基准测通用能力，自建评测集测业务场景；环境沙箱化保证可复现；同时报告成功率、pass^k、步数、费用；失败按原因人工分类，指导下一步优化；每次改动用配对检验判断是否真的有提升。
